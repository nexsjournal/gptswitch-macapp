## 3. 待验证技术问题

这些是后续开发实验要回答的问题，不要求用户现在逐条做决定。

| ID | 问题 | 当前合理基线 | 验证方式 |
| --- | --- | --- | --- |
| Q01 | 本机和 Windows Desktop 是否直接接受自有目录 | 优先官方配置 | G0 原生 UI + 请求捕获 |
| Q02 | 新模型目录如何刷新 | 预计启动时加载，集中一次重载 | 分别测窗口、app-server、全应用 |
| Q03 | 新旧任务的 provider 如何继承 | 不假设旧任务自动迁移 | 同任务切换与新任务对比 |
| Q04 | `auth.command` 在目标 Desktop 中是否可用 | ~~新宿主优先 helper，旧版 env 注入~~ **app-server 层已通过** | ✅ 2026-09-18：`codex-cli 0.155.0-alpha.2.6` 实际调用 helper（`--instance local-main`），凭 helper 输出通过上游鉴权；证据 [.local/g0-apply-pipeline.json](.local/g0-apply-pipeline.json)。Desktop GUI 与 token refresh 仍未验证 |
| Q05 | 自定义 reasoning 字符串菜单是否接受 | 使用模型声明和宿主交集 | 非标准档位 fixture |
| Q06 | 每模型 context 是否被全局覆盖 | 优先目录，显示全局冲突 | 读取 effective config 与上下文行为 |
| Q07 | 上游 compact / opaque continuation 是否兼容 | 未支持则明确拒绝，不伪造 | 长上下文与续接测试 |
| Q08 | 星算助手 Rust 后台具体如何应用配置 | 仅有 IPC/字符串线索，保持未知 | 只在公开源码或授权测试条件满足时深入 |
| Q09 | CodexSplit 用户现场校准为何失败 | 多状态协调是可能机制，非定论 | 后续另立脱敏日志复现，不在文档轮修改现场 |

2026-09-18 现场证据（macOS / ChatGPT Desktop / OpenCodex CLI Egress）：一次真实卡死可复现为**本地 Egress 桥接进程自身卡住**，而不是上游网关不可用。观测到的事实：宿主启动的 `codex-provider-bridge.js`（CLI Egress）在**两个本机 loopback 实例**上均**完成 TCP 握手但从不返回任何 HTTP 响应**（连同步就该返回 404 的未知路由也不响应），主线程空转在 `kevent`，进程无任何对外连接；与此同时，本机供应商网关的 `/health` 正常返回 200，其上游 HTTPS 端点也可达。对应的 Codex 会话在该桥接上一次模型响应成功之后即停止写入，随后被中断。

> 本节刻意不记录具体端口、进程号与供应商域名：结论不依赖这些数值，而它们属于使用者本机信息。需要复现时用 `lsof -nP -iTCP -sTCP:LISTEN` 找出本机桥接端口，再对该端口发一个本应立刻 404 的请求即可判定。

对本项目的影响与沿用结论：
- “本机中间层是单点”这一风险等级为**高**，且故障形态是**静默挂起（accept 但不应答）**，不是连接被拒。因此网关与 Egress 都必须有请求级超时、健康探测和“可判定失败”，不能依赖连接错误暴露问题。
- 不把该现象当作“多状态协调”的定论；只记录可复核的观测项（进程、端口、socket 状态、栈、健康端点响应）。
- 本项目的 `plan/execute` 已要求 CAS 与超时判定；实现网关时（G3）必须同时给出卡死可检出、可恢复的验收用例。

## 4. 可延后确认的产品选择

当前假设：中文优先、个人本地工具、暗色默认、无云账号体系、macOS arm64 + Windows x64 首发、Lucide 图标、API Key 为主要认证方式。可在开发前调整的事项包括最终名称、正式发布系统最低版本、首批真实供应商、是否必须同菜单保留官方订阅。

若“官方订阅与所有第三方模型必须在同一菜单且免切模式”成为硬要求，应把 Bridge 共存验证提到 G0 阻断门槛，并重新评估工期；不能保留原工期却删减隔离测试。

2026-09-18 补充：星算助手迁移原因采用用户转述；DSH 源码确认 Electron 主要承载自己的 Web 界面。当前网站外开是本方案基于既有范围的判断，不是用户对未来浏览器需求的明确否定。已有核心功能无需用户先理解框架名词；若未来需要内嵌控制台、多标签和独立登录，再按 [桌面壳复审](../research/03-desktop-shell-decision.md) 更新选型。

## 5. 文档更新规则

每次实验将结论从“待验证”更新为具体平台/版本的“通过或不支持”，附证据路径、日期和测试范围。不要把单次版本成功扩展成全版本支持；不要把用户填写值升级成官方事实。源码变化记录新 SHA，不覆盖旧报告使其失去可追溯性。
